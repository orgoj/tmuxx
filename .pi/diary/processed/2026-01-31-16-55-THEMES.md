## Task Summary
The user wanted to implement color templates (themes) for the application using a KISS approach, moving beyond hardcoded colors to a system of named themes that can be switched at runtime.

## Work Done
- **Named Themes**: Implemented a map-based theme system in configuration.
- **Predefined Themes**: Created `default`, `nord`, `monochrome`, and a "crazy" `cyberpunk` theme.
- **Runtime Switching**: Added `Action::NextTheme` bound to `Ctrl+t` to cycle through available themes.
- **Global Overrides**: Added `[theme_override]` section in `config.toml` to allow changing specific colors across all themes.
- **Background Support**: Added support for global background color (`bg`).
- **UI Refactoring**: Updated all components (`AgentTree`, `PanePreview`, `Header`, `Footer`, `MenuTree`, `ModalTextarea`, `PopupInput`) to respect the active theme.
- **Version Bump**: Bumped project version to `0.5.0` to mark the major feature release.

## Design Decisions
- **Themes Map**: Used a `HashMap<String, ThemeConfig>` to allow users to define multiple named themes.
- **Styles Bridge**: Created a `Styles` struct that pre-calculates `ratatui::Style` and `Color` objects from string-based configuration once per config load/theme switch, improving rendering performance.
- **Overlay Logic**: Implemented a two-step application in `PartialConfig::apply`: first load named theme, then overlay `theme_override` settings. This satisfies the "change just one color" requirement.
- **Explicit BG Fill**: Added explicit `Block` rendering with theme background color at the start of the `Terminal::draw` call to support real dark/light themes.

## Challenges & Solutions
| Challenge | Solution |
|-----------|----------|
| TOML duplicate key error | `theme` was used as a string (selector) and a table (overrides). Renamed table to `theme_override` to avoid collision. |
| Shadowing in code | `ctx` (AgentRenderCtx) was being shadowed by `ctx` (context percentage) in `agent_tree.rs`, causing type errors. Renamed the latter to `percent`. |
| Missing Styles param | Many UI components needed access to `state.styles`. Passed the reference through constructors and render methods. |

## Mistakes & Corrections
### Where I Made Errors:
- **Incomplete Initial Design**: My first proposal just grouped colors into a `[theme]` section without support for multiple named sets. The user corrected me that themes should be named and switchable.
- **Shadowing & Types**: I introduced a shadowing bug in `agent_tree.rs` during a surgical edit that broke compilation.
- **TOML Syntax**: I wrote a `config.toml` that was invalid because it tried to use `theme` as both a key and a table header.

### What Caused the Mistakes:
- **Misunderstanding of "Template"**: I initially interpreted "template" as "config section" rather than "named profile".
- **Hasty Surgical Edits**: Variable shadowing usually happens when copying logic without carefully checking local scopes.

## Lessons Learned
### Technical Lessons:
- **TOML Rules**: A key cannot be both a leaf value and a table name in the same scope.
- **Ratatui Theme Patterns**: Since Ratatui is stateless regarding styles, a central `Styles` object in the application state is the cleanest way to implement themes.
- **String Color Parsing**: Created a robust `parse_color` utility that handles names, hex codes (`#RRGGBB`), and `rgb(r,g,b)` formats.

### To Remember for CLAUDE.md:
- Themes are now defined in `themes` map.
- `theme` key is the active selector.
- `theme_override` is for global tweaks.
- Selection indicator prefers `bar` mode with `█` and `none` background as per user preference.
